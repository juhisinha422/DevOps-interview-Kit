## 🔹 How do you write and structure a Jenkins Shared Library for reusable pipelines?

A Jenkins Shared Library is used to **standardize and reuse pipeline logic across multiple projects**. It helps avoid duplication and ensures consistency.

### Structure

```id="1a2b3c"
(root)
│
├── vars/
│   └── buildPipeline.groovy
│
├── src/
│   └── com/company/utils.groovy
│
└── resources/
```

* **vars/** → reusable pipeline functions (entry point)
* **src/** → Groovy classes for complex logic
* **resources/** → static files (configs, templates)

### Example (vars/buildPipeline.groovy)

```groovy id="4d5e6f"
def call() {
    pipeline {
        agent any
        stages {
            stage('Build') {
                steps {
                    echo "Building application..."
                }
            }
        }
    }
}
```

### Usage in Jenkinsfile

```groovy id="7g8h9i"
@Library('my-shared-lib') _
buildPipeline()
```

✅ **Interview Point:**
Shared libraries improve **reusability, maintainability, and governance** across pipelines.

## 🔹 After a SonarQube scan, how can you print the dashboard URL along with Quality Gate status inside the pipeline?

After running SonarQube analysis, Jenkins provides a method to check Quality Gate status.

### Example

```groovy id="sonar1"
stage('SonarQube Analysis') {
    steps {
        withSonarQubeEnv('SonarQube') {
            sh 'mvn sonar:sonar'
        }
    }
}

stage('Quality Gate') {
    steps {
        timeout(time: 5, unit: 'MINUTES') {
            def qg = waitForQualityGate()
            echo "Quality Gate Status: ${qg.status}"
            echo "Sonar Dashboard: ${env.SONAR_HOST_URL}/dashboard?id=${env.JOB_NAME}"
        }
    }
}
```

✅ **Interview Point:**

* `waitForQualityGate()` ensures pipeline fails if quality gate fails
* Dashboard URL helps developers quickly review issues

## 🔹 Given a deployment.yml, how would you extract and print the Docker image being used?

You can extract the image using tools like **grep, awk, or yq**.

### Example deployment.yml

```yaml id="dep1"
containers:
  - name: app
    image: myapp:v1
```

### Using grep

```bash id="dep2"
grep "image:" deployment.yml
```

### Using yq (recommended)

```bash id="dep3"
yq e '.spec.template.spec.containers[].image' deployment.yml
```

### Jenkins Pipeline Example

```groovy id="dep4"
def image = sh(script: "yq e '.spec.template.spec.containers[].image' deployment.yml", returnStdout: true).trim()
echo "Docker Image: ${image}"
```

✅ **Interview Point:**
Use **yq** for structured YAML parsing instead of plain text tools.

## 🔹 While building a Docker image for a Java app, what JAR file path do you typically use and why?

Typically, the JAR file is located inside the **target/** directory because it is generated by build tools like Maven or Gradle.

### Example

```dockerfile id="jar1"
FROM openjdk:17-jdk-alpine
WORKDIR /app
COPY target/myapp.jar app.jar
CMD ["java", "-jar", "app.jar"]
```

### Why?

* `target/` is the **default Maven build output directory**
* Ensures we use the **latest compiled artifact**
* Keeps Dockerfile aligned with CI/CD build process

✅ **Interview Point:**
Always copy **only the final artifact**, not the entire project, to keep images lightweight.

## 🔹 What happens if the Kubernetes API Server goes down? Explain the impact on cluster operations.

The Kubernetes API Server is the **control plane entry point**. If it goes down:

### Impact

* `kubectl` commands will **stop working**
* No new deployments, scaling, or updates can be performed
* Controllers (like scheduler) cannot communicate
* Cluster state cannot be modified

However:

* Existing running pods **continue running**
* Node-level operations continue

✅ **Interview Point:**
Control plane failure affects **management**, not **existing workloads immediately**.

## 🔹 If the API Server is down, will application traffic stop or continue flowing? Why?

Application traffic will **continue flowing** even if the API server is down.

### Reason

* Kubernetes networking (kube-proxy / CNI) works at node level
* Services and iptables rules are already configured
* Pods continue serving traffic independently

### Impact

* No new deployments or scaling
* Existing services continue handling traffic

✅ **Interview Point:**
Kubernetes separates **control plane (management)** and **data plane (traffic)**.

## 🔹 How do you write a Docker multi-stage build, and what are its advantages?

A multi-stage build uses multiple `FROM` statements to separate **build and runtime environments**.

### Example

```dockerfile id="multi1"
# Build stage
FROM maven:3.8.6-openjdk-17 AS build
WORKDIR /app
COPY . .
RUN mvn clean package

# Runtime stage
FROM openjdk:17-jdk-alpine
WORKDIR /app
COPY --from=build /app/target/myapp.jar app.jar
CMD ["java", "-jar", "app.jar"]
```

### Advantages

* Smaller image size
* No unnecessary build tools in final image
* Improved security
* Faster deployments

✅ **Interview Point:**
Multi-stage builds help create **lean, production-ready images**.
