# Jenkins Interview Questions & Answers – 4 Years Experience

## 1️⃣ What is Jenkins, and why is it used in CI/CD?

Jenkins is an open-source automation server mainly used to automate software development processes such as building, testing, packaging, and deploying applications. It is widely used in CI/CD because it can integrate with tools like GitHub, GitLab, Maven, Gradle, Docker, SonarQube, AWS, Kubernetes, and Terraform. In a typical CI/CD setup, developers push code to GitHub, which triggers Jenkins through a webhook. Jenkins then checks out the code, performs code quality and security checks, builds the application, creates a Docker image, pushes it to a container registry such as Amazon ECR, and finally deploys the application to Kubernetes or Amazon EKS. Jenkins helps reduce manual effort, provides consistent deployments, and gives visibility into the entire software delivery process.

## 2️⃣ What is the difference between a Freestyle Job and Pipeline in Jenkins?

A Freestyle Job is a traditional Jenkins job where we configure build steps, source code management, triggers, environment variables, and post-build actions through the Jenkins UI. It is simple and suitable for basic automation, but maintaining complex jobs can become difficult because the configuration is stored mainly in Jenkins. A Pipeline, on the other hand, allows us to define the complete CI/CD workflow as code, usually inside a Jenkinsfile stored in Git. Pipelines support stages, conditions, parallel execution, approvals, error handling, and deployment steps. For example, I would prefer a Pipeline for a production project because the CI/CD process becomes version-controlled, reusable, auditable, and easier to maintain.

## 3️⃣ How do you create a Jenkins Pipeline using a Jenkinsfile?

To create a Jenkins Pipeline using a Jenkinsfile, I first create a file named `Jenkinsfile` in the application Git repository. Inside the Jenkinsfile, I define the pipeline stages such as checkout, build, test, Docker image creation, image push, and deployment. For example, the pipeline could contain stages such as `Checkout`, `Build`, `Test`, `Docker Build`, `Push Image`, and `Deploy`. After committing the Jenkinsfile to Git, I create a Pipeline or Multibranch Pipeline job in Jenkins and configure it to use the Git repository. Jenkins then reads the Jenkinsfile and executes the defined stages. I prefer storing the Jenkinsfile in Git because any changes to the CI/CD process are version-controlled along with the application code.

## 4️⃣ What is the difference between Declarative Pipeline and Scripted Pipeline?

Declarative Pipeline and Scripted Pipeline are two ways of writing Jenkins pipelines. Declarative Pipeline follows a predefined and structured syntax using blocks such as `pipeline`, `agent`, `stages`, `steps`, `environment`, and `post`, which makes it easier to read and maintain. Scripted Pipeline is based on Groovy scripting and provides more flexibility for implementing complex logic and dynamic workflows. For most enterprise CI/CD pipelines, I prefer Declarative Pipeline because it provides a clear structure and is easier for teams to understand and maintain. I would use Scripted Pipeline when the pipeline requires advanced Groovy-based logic that is difficult to implement using the Declarative syntax.

## 5️⃣ How do you configure and use Jenkins Agents/Slaves?

Jenkins Agents, previously called Jenkins Slaves, are machines or environments where Jenkins executes build and deployment tasks while the Jenkins Controller manages the overall pipeline. I configure an agent by adding it under Jenkins node or agent configuration, defining its name, labels, working directory, and connection method. Depending on the environment, agents can be connected using SSH, inbound agents, or dynamically provisioned environments such as Kubernetes. For example, I can create separate agents with labels such as `docker`, `linux`, or `kubernetes` and then use the appropriate label in the Jenkinsfile. In a production environment, using agents helps distribute workloads, isolate builds, and prevent heavy build processes from consuming resources on the Jenkins Controller.

## 6️⃣ A Jenkins build is stuck in Queue. How would you troubleshoot it?

If a Jenkins build is stuck in the queue, I first check the queue message because Jenkins usually provides the reason, such as no available executor, an offline agent, a label mismatch, or a blocked resource. I then check **Manage Jenkins → Nodes/Agents** to verify whether the required agent is online and whether it has available executors. I also check whether the pipeline is requesting a label for which no agent is currently available. If the agent is offline, I check its connectivity, disk space, CPU, memory, and Jenkins agent logs. I also verify whether another build is consuming all executors or whether there are resource restrictions such as throttling or locks. After identifying the issue, I bring the agent back online, increase executors or provision additional agents if required, and then rerun the build.

## 7️⃣ A Jenkins pipeline fails while building a Docker image. How would you troubleshoot the issue?

If a Jenkins pipeline fails during Docker image creation, I first check the Jenkins console output to identify the exact Docker error. I verify that Docker is installed and running on the Jenkins agent and that the Jenkins user has permission to communicate with the Docker daemon. Next, I validate the Dockerfile, build context, base image, required files, and package installation commands. I also check whether the required base image is available and whether the Jenkins agent has network connectivity to Docker Hub or the configured container registry. Disk space is another important check because Docker builds can fail when the agent runs out of storage. I would reproduce the same `docker build` command directly on the agent if possible, fix the root cause, clean unused Docker resources if required, and rerun the pipeline.

## 8️⃣ How do you securely manage AWS credentials, SSH keys, and secrets in Jenkins?

I securely manage credentials using Jenkins **Credentials Manager** rather than hardcoding passwords, AWS access keys, SSH keys, or tokens inside the Jenkinsfile. I create credentials with appropriate types such as AWS credentials, username/password, SSH private keys, or secret text and then reference them using Jenkins credential IDs. For example, AWS credentials can be injected into a pipeline only for the required stage using Jenkins credentials mechanisms. I also make sure that secrets are masked in Jenkins console logs and avoid printing sensitive environment variables. For enterprise environments, I prefer integrating Jenkins with a dedicated secrets manager such as AWS Secrets Manager or HashiCorp Vault when appropriate. I follow the principle of least privilege by giving Jenkins only the permissions required for the specific deployment instead of using highly privileged AWS credentials.

## 9️⃣ How do you implement GitHub → Jenkins → Docker → Kubernetes/EKS CI/CD?

I implement this CI/CD flow by configuring a GitHub webhook to trigger Jenkins whenever code is pushed or a pull request is merged. Jenkins checks out the source code and executes the Jenkinsfile. The pipeline first performs code validation and testing, followed by building the application. It then creates a Docker image with a unique tag such as the Git commit SHA and pushes the image to Amazon ECR or another container registry. After the image is successfully pushed, Jenkins updates the Kubernetes deployment manifest or Helm values with the new image tag and deploys it to the Amazon EKS cluster using `kubectl` or Helm. Finally, Jenkins verifies the deployment using commands such as `kubectl rollout status` and checks pod and application health. If the deployment is successful, the pipeline completes; otherwise, the deployment stage fails and rollback procedures can be triggered.

## 🔟 A production deployment fails after a Jenkins pipeline completes successfully. How would you troubleshoot and roll back the deployment?

If Jenkins reports a successful deployment but the production application is failing, I first separate the CI/CD problem from the application or infrastructure problem. I check the Kubernetes deployment, pods, ReplicaSets, events, services, ingress, and application logs using commands such as `kubectl get pods`, `kubectl describe pod`, `kubectl logs`, and `kubectl get events`. I also verify readiness and liveness probes, service endpoints, configuration, secrets, environment variables, resource limits, and application connectivity to databases or external services. If the new release is confirmed as the cause, I immediately roll back to the last known good version to reduce production impact. For a Kubernetes Deployment, I can use `kubectl rollout history` to review revisions and `kubectl rollout undo deployment/<deployment-name>` to roll back. After rollback, I verify pod health, application endpoints, logs, and monitoring dashboards. Once production is stable, I investigate the root cause, document the incident, and fix the pipeline or application issue before attempting another deployment.
